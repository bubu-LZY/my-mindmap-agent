# 大纲与关联图性能优化改动方案

> 状态：待立项评审（未实施）
> 关联背景：大文件（节点数 > 数千）场景下，大纲视图与关联图视图存在明显卡顿。本文给出两个独立可拆分的优化方案，供判断「风险 / 收益」后决定是否立项。

---

## 一、大纲视图：el-tree → el-tree-v2（虚拟滚动）

### 1. 现状

- 文件：`src/components/OutlineView.vue`
- 当前实现：使用 Element Plus 的 `el-tree`（**非虚拟滚动**），通过 `:data="treeData"` 一次性渲染整棵树。
- 渲染开销：每个节点一个 DOM 行，且每行内部还有 `indent-guides`（层级竖线）、`node-text`（contenteditable）、图片/备注/概括/关联等内联图标。节点数越大，DOM 数量与重排成本线性增长。
- 交互依赖（改造时必须保留的能力）：
  - `draggable` 拖拽排序（`@node-drop="onNodeDrop"`），这是大纲的核心功能。
  - `contenteditable` 行内编辑（`node-text`）。
  - 层级竖线 `indent-guides`（按 `node.level` 手工绘制）。
  - `default-expanded-keys` 折叠状态恢复。

### 2. 改动点

1. 将 `el-tree` 替换为 `el-tree-v2`（Element Plus 虚拟滚动树）。
2. 适配虚拟滚动必需的 `height`（容器高度）与 `item-size`（行高，需与现有行高一致）。
3. 重写插槽：`el-tree-v2` 的 `#default="{ node, data }"` 中 `node` 结构与 `el-tree` 不同（`level`、`expanded`、`isLeaf` 等字段语义需核对），`indent-guides` 的 `left` 偏移计算需按新 `node.level` 重算。
4. 折叠状态恢复：`el-tree-v2` 用 `default-expanded-keys` 的兼容性需验证；必要时改由受控 `expanded-keys` + 手动展开恢复。

### 3. 关键风险（必须正视）

| 风险 | 说明 | 影响 |
| --- | --- | --- |
| **el-tree-v2 不支持 `draggable`** | 官方 TreeV2 未提供与 el-tree 同等的拖拽排序能力 | 大纲的拖拽排序需**自行实现** HTML5 拖拽或另寻方案，工作量显著增加 |
| 行内编辑交互 | `contenteditable` 在虚拟滚动下的焦点/重渲染行为需重新验证 | 可能出现编辑中因滚动导致焦点丢失 |
| 缩进线 | `indent-guides` 是手绘的竖线，依赖 `node.level` 与缩进像素强耦合 | 需逐像素重算，回归风险高 |
| 固定行高约束 | 虚拟滚动依赖 `item-size` 恒定行高；当前节点含图片/备注图标可能造成行高不一致 | 需统一行高，否则错位 |

### 4. 替代/降级方案（可选）

- **方案 B**：保留 `el-tree`，改为「懒加载 / 按需展开」——仅当节点展开时才渲染子节点。改动小、保留拖拽能力，但展开大量节点时卡顿仍在。
- **方案 C**：仅对「超大节点数」场景启用虚拟滚动分支，小图仍走 `el-tree`，降低回归面。

## 二、关联图：数量截断 → 层级剪枝

### 1. 现状

- 文件：`src/components/GraphView.vue`
- 当前实现：`render()` 内已有「超大图降级」，但策略是**数量截断**（深度优先取前 `MAX_RENDER_NODES` 个节点，超出部分直接丢弃并置 `truncated = true`）。
- 问题：截断是「数量」维度，不是「层级」维度——可能把用户当前关注的深层叶子砍掉、却保留了无关的浅层节点；且截断后看不到「还有多少层被隐藏」的语义。

### 2. 改动点（层级剪枝）

1. 新增「最大渲染深度」参数（如 `MAX_RENDER_DEPTH = 3`）。
2. `buildGraphData()` 阶段按 `depth` 过滤：仅渲染 `depth <= MAX_RENDER_DEPTH` 的节点与边。
3. 降级策略：若 `depth == MAX_RENDER_DEPTH` 的节点数量仍超过阈值，自动把 `MAX_RENDER_DEPTH` 降为 2（即「第 3 层太多就只显示到第 2 层」）。
4. 被剪掉的深层节点，在其父节点上渲染「折叠/展开」标记，点击可局部展开该分支的下一层。
5. 保留现有 `MAX_RENDER_NODES` 作为兜底上限（防止层级剪枝后仍有极端大图）。

### 3. 关键风险

| 风险 | 说明 | 影响 |
| --- | --- | --- |
| 剪枝后拓扑变化 | 砍掉深层节点后，力导向布局的连线/受力改变，可能引起整图重排跳动 | 需保证剪枝前后布局稳定 |
| 折叠标记交互 | 需新增「局部展开」交互，与现有 `locate-node`/`zoomToFit` 联动 | 交互路径变长 |
| 与「数量截断」的优先级 | 层级剪枝与数量截断需明确谁先谁后、阈值如何联动 | 逻辑复杂度上升 |

---

## 三、建议

两个方案相互独立，可分别立项、分别灰度：

1. **关联图「层级剪枝」风险较低、收益直接**（大图从「随机截断」变为「有语义的层级折叠」），建议优先。
2. **大纲「el-tree-v2」风险较高**（核心拖拽排序需重写），建议先做小范围验证，或优先采用「懒加载（方案 B）」作为过渡。
